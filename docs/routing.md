# 工具路由策略

状态：2026-11-14 实测定稿，默认启用。实现在 `internal/gateway/routing_strategy.go`（第一步和第三步）、`internal/gateway/decisions.go`（第二步和 Decisions 调用）、`internal/gateway/discovery.go`（串联）。实验记录在 `evals/routing/NOTES.md`，本文只写结论。

## 1. 问题

网关只向 Agent 暴露 `discover_tools`、`get_tool_schema`、`invoke_tool` 三个工具。`discover_tools` 收到一句自然语言意图，要从所有已启用的工具（目前 14 个服务、391 个只读工具）里挑出一小组真正需要的，返回它们的定义。挑选由 Decisions 模型完成：它不生成文本，只对给定输入回答一组问题，每题返回概率。

约束：

- 意图常是中文，工具描述是英文，关键词检索对不上，已经删掉。
- Decisions 的是非题彼此独立，一道题看不见另一道题，表达不了「这几个里选一个」。
- 输入 token 按分钟限速，成本随候选数线性增长（约 0.2k token/工具）。
- 分数对输入格式敏感，固定阈值不可靠。

目标是精度 ≥ 95%，同时召回不降。

## 2. 三步策略

### 第一步：按服务收窄（`hierarchical`）

输入一个 JSON：`{intent, context, services:[{id, name, description, tools:[工具名…]}]}`，意图在前。每个服务一道是非题：「服务 X 是否提供直接服务于当前任务的工具（含必要的标识符查找）？按它的描述和工具名判断。」

规则：概率 ≥ 0.5 的服务进入下一步，按概率排序最多 3 个；都不够 0.5 时取最高的一个，让下一步决定。只有一个服务时跳过；请求带 `services` 参数时也跳过，直接限定在指定服务内。

效果：单次请求的候选数由最大的服务决定，而不是所有工具之和。在 83 道正例里从未丢掉正确服务。开销随服务数增长（14 个服务约 6k token），与工具数无关。

### 第二步：逐工具是非题

输入 `{intent, context, candidates:[{id, server_id, name, description, tags, read_only}]}`，用 struct 保证意图在候选之前（map 会按键排序把意图挤到几千 token 之后，一个工具的分数曾因此从 0.93 掉到 0.46）。每个工具一道题，题里用工具 ID 点名，不用 `candidates[i]`（序号在 151 个工具时模型数不准，精度 29%）。规则文本在每道题里重复，省一次就掉 8–12 个点。

概率 ≥ 0.5 的过线，按概率排序，最多 8 个进入第三步。

### 第三步：精选（`refine`）

过线的候选再问一道 choice 题：「哪一个候选最直接完成当前任务？」选项是每个候选的 ID 和描述首行，外加「都不是」。模型返回整个分布。

返回规则：

1. 胜出的工具一定返回；其他候选的占比不低于胜者一半的也返回。两个同样直接的工具（`count_pageviews` 和 `aggregate_pageviews`）会一起回；相邻但次要的（`get_project_trace` 对 `get_runtime_errors`，24% 对 55% 的 Sentry 发布详情）不会。
2. 「都不是」胜出时，看第二步：若有候选相关性 ≥ 0.9，忽略「都不是」，仍按分布返回。choice 题只能选一个，任务需要两个工具（Supabase 的 URL 和 key）或几个服务各有一个同样对的工具时，它就会答「都不是」。
3. 否则，若过线候选来自多个服务，返回 `needs_context`，`question` 里列出这些服务，提示用 `services` 参数指定。
4. 否则 `no_match`。

效果：Vercel 单服务 151 个工具的精度从 81% 到 100%，召回不变。多一次调用，输入 300–2,000 token。

## 3. 数据

默认配置，14 个服务、391 个工具，一次运行：

| 评测 | 召回 | 精度 | no_match | token/次 |
| --- | --- | --- | --- | --- |
| multi.json，61 题 | 55/55 | 100% | 6/6 | 15,485 |
| github.json，20 题 | 16/17 | 100% | 3/3 | 13,662 |
| vercel.json，24 题 | 21/21 | 100% | 3/3 | 39,377 |

对照：同样 352 个工具平铺路由加精选，92,810 token/次，精度 98%。

四道召回失败都是意图在几个服务之间同样成立（「我是谁」「我的团队」「v1.2.0 的发布说明」在 GitHub、Vercel、Sentry、Linear 之间），网关返回 `needs_context`，评测把这种答案标为可接受。

## 4. 试过并否决的

- 关键词检索、BM25：中文意图对不上英文描述。pi 用 BM25，但它的用户是主模型，查询词和描述同语言。
- 把参数名加进候选摘要：精度 81% → 71%。`projectId`、`teamId` 这类公共参数让查找类工具也显得相关。pi 的排序器读属性名是为了匹配查询词，是非题却把它当相关性证据。
- 调阈值：噪声工具概率 53–86%，正确工具 71–99%，有重叠，没有一个阈值能分开。
- 按名字前缀在服务内再分一层：Vercel 分出 68 组、43 组只有一个工具，噪声工具和正确工具大多不在同一组。
- 规则只写一次：省 26–30% token，掉 8–12 个点。

## 5. 接口

- 请求：`intent`、`context`、可选 `services`（服务 ID 列表，限定范围并跳过第一步）。
- 响应：`status` 为 `selected` / `needs_context` / `no_match`；`servers` 是第一步选中的服务；每个工具的 `reason` 写明第二步概率和第三步占比；`prompt_tokens` 是三步之和。
- 开关：`GATEWAY_ROUTING` 不设即全开；`flat` 只留第二步；`hierarchical`、`refine` 单开。

## 6. 已知限制

- 阈值（0.5 过线、占比 ≥ 胜者一半、0.9 覆盖线）在这 105 道题上定的，题目是读过工具列表后写的，没有在未见过的意图上验证。每种配置只跑过一次，模型本身是确定的。
- 只测了 `gemini-decision-1`。OpenAI 的 Decisions 接口单次 100 题的上限未验证；若它不返回 choice 的概率分布，第三步退化为只返回胜者。
- 最大的服务（Vercel 151）仍超过 100 题上限，超限模型需要分片，未实现。
- 服务数再增长时第一步开销线性上涨；几十个服务以上要在服务层之上再分一层，或改用 embedding 做召回。
- 「包含标识符查找」这条规则会把 `list_projects` 带进来，精选压住了它，但规则本身没变。
- 新接的 11 个服务用占位凭据导入，只能路由不能执行；Figma 未授权。
